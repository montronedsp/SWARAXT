# Governance

SWARA XT is a small, independently maintained FLOSS project. Its governance is
intentionally lightweight and is designed to keep technical decisions visible
and reviewable in the repository.

## Maintainer and roles

The current project maintainer is **MontroneDSP**. The project identifies
Andrea Montrone as its author. There is no claim of a second maintainer or of
redundant release access.

The maintainer is responsible for project direction, code review and merge
decisions, release authorization, responding to conduct and security reports,
and protecting the project's technical and licensing boundaries.

Contributors are responsible for submitting work they are entitled to share,
following the contribution guide and Code of Conduct, preserving provenance,
and supplying focused evidence for behavioral or DSP changes.

## Decision making and review

Technical discussion normally happens in public issues and pull requests.
The maintainer makes final decisions after considering evidence, compatibility,
maintenance cost, and the project's stated scope. Non-trivial contributions are
reviewed before merge; the depth of review is proportional to their risk.

Only the project maintainer can approve and merge changes to the canonical
repository or authorize an official release. Releases are authorized after the
maintainer has reviewed the intended source state and applicable validation.

## Security-sensitive decisions

Potential vulnerabilities, dependency risks, release-integrity concerns, and
reports that could expose users should be handled through the private reporting
path in [SECURITY.md](SECURITY.md). The maintainer decides when public
disclosure is appropriate and coordinates fixes with affected contributors when
needed.

## Disagreements

Participants should first seek resolution through respectful, evidence-based
discussion. If disagreement remains, the maintainer makes the final decision.
Conduct concerns follow [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).

## Changing this document

Governance changes are made through a documented repository change reviewed and
approved by the project maintainer. Material changes should explain their
motivation in the associated issue, pull request, or commit.
